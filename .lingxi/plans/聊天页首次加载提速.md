# 聊天页首次加载提速方案

## 一、问题根因

进入聊天页后消息显示慢，是「同步阻塞了显示」与「渲染低效」叠加造成的：

1. **同步阻塞消息显示（核心）**：`ChatViewModel.onUiStarted()` 中，`repository.syncNow()` 在 `collectMessages()` 之前顺序执行。`syncNow()` 首次会串行完成匿名登录、上传 pending、`fetchMessages(conversationId, 0)` 全量拉取历史消息、逐条串行下载图片/语音、再依次拉取 participants/weeklyReports/background，全部结束后才从本地 Room 读出消息渲染。
2. **首次同步全量拉取**：`previousSyncTime == 0` 时 `fetchMessages` 用 `after=0` 拉取全部历史消息。
3. **媒体串行下载**：`fetchMessages` 结果用 `map { downloadMedia(...) }` 逐条顺序下载，N 条媒体 = N 次串行 HTTP。
4. **图片无下采样解码**：`MessageBubble`、`ChatScreen`（背景）、`AvatarBadge`（头像）都用 `BitmapFactory.decodeFile` 直接解码原图，大图卡顿且耗内存。
5. **LazyColumn 无 key + O(n²)**：`items(messages.size)` 无 key；每个 item 内用 `firstOrNull`/`filter` 线性查找引用消息与打卡回复。

## 二、优化方案

### 改动 1：解耦「消息显示」与「网络同步」（ChatViewModel.kt，核心）

`onUiStarted()` 调整执行顺序：先 `ensureInitialized()`（纯本地操作，含一次 legacy 迁移 + conversation upsert），随后**立即并行启动三个本地数据收集**（Room 的 Flow 会立即 emit 本地已存消息），再执行 `syncNow()`（后台），最后启动媒体预取与周期同步循环。

要点：
- `collectMessages()` / `collectParticipants()` / `collectBackground()` 放在 `syncNow()` 之前 launch。
- 本地已缓存的消息会即刻渲染，实现文字消息秒开；同步完成后 Room 数据变化通过 Flow 自动增量刷新 UI。
- `syncNow()` 内部已有 `syncMutex`，与周期循环（每 1 秒一次）天然串行，不会并发冲突。

### 改动 2：同步不再串行下载媒体，改为后台预取（ChatRepository.kt）

- 在 `syncNowWithOutcome()` 中，删除 `fetchMessages` 结果里 `map { downloadMedia(...) }` 的串行下载循环，只做 `upsertAll` 元数据（`mediaPath` 保留远程相对路径）。
- 新增 `suspend fun prefetchRecentMedia()`：只对「最近 3 天窗口（与 `observeRecent` 的 `RECENT_WINDOW_MS` 一致）内、`mediaPath` 非本地文件」的图片/语音消息，逐个下载到本地缓存，并用 `messageDao().updateMediaPath(id, localPath)` 更新本地路径，从而触发 Room Flow 刷新 UI。
- 该预取在 `syncNow()` 完成后由 ViewModel 单独 `launch`，不与 `syncMutex` 争抢，也不阻塞消息显示；下载失败单条跳过不中断。

### 改动 3：图片改用 Coil 下采样渲染（MessageBubble / ChatScreen / AvatarBadge）

项目已引入 `coil-compose` 且 `PetActivity` 已有 `AsyncImage` 用法。将三处 `BitmapFactory.decodeFile(...).asImageBitmap()` 替换为 `AsyncImage(model = File(path))`：
- 图片消息气泡、聊天背景、头像。
- Coil 自动按目标尺寸下采样、做内存/磁盘缓存，消除大图解码卡顿与 OOM 风险。
- 本地文件尚未下载完成时显示占位（灰块/默认头像），文件就绪后经改动 2 的 `updateMediaPath` 自动刷新。
- 需确认 `FoxChatApplication` 中自定义 `ImageLoader` 保留了默认 `FileFetcher`（默认 `.components {}` 是在默认组件基础上追加，一般无需额外配置；若加载本地文件异常则显式补 `add(FileFetcher.Factory())`）。

### 改动 4：LazyColumn 加 key + 预计算映射消除 O(n²)（ChatScreen.kt）

- `items(messages, key = { it.id })`，保证增量更新只重组变化项。
- 用 `remember(messages)` 预计算 `messageById = messages.associateBy { it.id }` 与 `checkinRepliesByMessageId = ...groupBy { it.replyToMessageId }`，item 内改为 O(1) 取值，替代 `firstOrNull`/`filter` 线性扫描。

### 改动 5（可选，次要）：DeviceIdentityStore 解密结果缓存

`isPaired` / `currentRole` / `currentConversationId` 每次访问都走一次 AndroidKeyStore 解密。可在 `DeviceIdentityStore` 内对解密结果做内存缓存（首次解密后缓存，写入时失效），减少启动路径与聊天页初始化中的重复 Keystore 开销。此改动对「消息显示慢」影响较小，作为可选优化项。

## 三、不做的事（控制范围）

- 不引入 FCM 或实时推送（README 已说明非实时同步属预期）。
- 不做历史消息分页/上滑按需加载（可作为后续增强，不在本次范围）。
- 不改动 `observeRecent` 的 3 天显示窗口逻辑。

## 四、验证方式

1. 冷启动进入聊天页，观察文字消息是否秒开（本地 Room 数据立即显示）。
2. 用含大量历史消息 + 图片/语音的账号对比优化前后进入页面的可交互耗时。
3. 观察图片是否逐步加载、内存占用是否稳定（无 OOM、无明显卡顿）。
4. 语音在文件未就绪时点击，确认仍走现有「语音文件未就绪」提示（已有逻辑，无需新增）。
5. 若需量化，可后续用 Android Studio Profiler / Macrobenchmark 记录冷启动与首帧耗时。

## 五、风险与权衡

- **媒体延迟加载**：图片/语音可能先显示占位，随后逐步就绪。这是用户已确认接受的取舍（优先秒开文字）。
- **预取窗口**：仅预取最近 3 天媒体，更早的历史媒体需后续按需加载增强（不在本次范围）。
- **Coil 与自定义 ImageLoader 兼容性**：若本地 File 加载异常，需显式补充 `FileFetcher` 配置（改动 3 已含兜底说明）。
